# 一、现在的效果应该怎样判断？

## 1. 不是“已经会跳，只差恢复”，而是当前 PPO 尚未稳定学会起跳

修正资产和重置问题之后，v2c 的结果如下：

| PPO 更新数 | 正式完整成功 | 非足端触地率 | 平均策略噪声 std |
|---:|---:|---:|---:|
| 200 | 0/400 | 0% | 0.7477 |
| 400 | 0/400 | 100% | 0.9021 |
| 600 | 0/400 | 100% | 1.1370 |
| 800 | 0/400 | 39.25% | 1.4932 |

最新模型不仅完整成功率为零，**合格跳跃落地也是 0/400，最大离地后 COM 升高只有约 9.58 mm**。因此，不能把当前失败主要归因于“0.8 秒恢复要求太严格”。最新策略首先就没有完成要求的跳跃。

这组结果也说明：**增加同配置训练步数没有产生单调改善。** 200 更新版本至少保持了较好的不触地表现，继续训练后却出现明显退化。它更像是优化方向、探索方式或奖励结构存在问题，而不是只差训练时长。这里是根据评测序列作出的判断，不是已经验证的因果结论。

## 2. 但也不能说 Go2 + PiPER 在当前模型中跳不起来

已有工程动作搜索及重放提供了另一类证据：

- 最初 256 条受限动作搜索中，有 17 条合格跳跃落地，但没有完整恢复。
- 后续精选动作重放中，32 条轨迹有 30 条合格跳跃落地，其中 **1 条完整恢复**。
- 该成功轨迹的 COM 上升约 **0.08656 m**、连续离地 **0.234 s**、连续恢复 **0.948 s**，且没有非足端地面接触。 

**这证明的是“当前仿真模型中已经观察到可行实例”，不是“已经有鲁棒跳跃控制器”，更不是“真机一定可行”。**

尤其值得注意：同组参数的另一条重放，连续恢复只有约 0.306 秒。这说明动作接近可行边界，恢复还不稳，不能只拿唯一成功实例做模仿就期待泛化。

所以现在最有用的判断是：

> **系统并非没有任何成功路径，而是当前 PPO 没有可靠发现和维持这条路径。**

# 二、我认为优先级最高的三个问题

## 问题一：主要恢复奖励没有要求“先完成合格跳跃”

这是本次审查中，我认为最应该先处理的一点。

### 当前代码实际在做什么？

`jump_metrics.py` 中，机器人经历约 20 ms 的离地后，再落地，就有机会设置 `landed_once`。之后，只要满足姿态、速度和支撑条件，`stable_recovery` 就可以成立；**它本身不要求这次跳跃达到 0.08 m 和 0.10 s 的正式标准**。

而 `jump_env.py` 又给予：

```python
3.0 * stable_recovery
+ 2.0 * recovery_quality
```

这两部分主要恢复奖励。`recovery_quality` 同样从 `landed_once` 出发，没有要求 `valid_jump_landed`。

### 我做的 CPU 测试发现了什么？

我给原始状态机输入了一个**合成状态序列**：

```text
有地面支撑
→ 离地 40 ms、COM 只升高约 2 mm
→ 落地后稳定 1 秒
```

结果是：

```text
valid_jump_landed = False
recovery_seen     = True
formal_success    = False
```

但按照当前两项恢复奖励的计算，该稳定阶段仍能累计得到约 **5.0 的恢复收益**，尚未计入其他奖励项。

:chatgpt-content-reference{index="25"}[查看实际 CPU 测试结果](sandbox:/mnt/data/quadsmash_g04_review/cpu_probe/results.json)

**这里必须准确区分：正式验收没有把失败误判为成功；偏差发生在训练奖励上。** 这个测试也不证明合成轨迹动力学可行，更不证明当前策略已经利用了这条奖励路径。

### 为什么这值得优先修？

你们真正要优化的是：

\[
\text{合格跳跃}\rightarrow\text{稳定恢复}
\]

但当前奖励允许另一条路线：

\[
\text{很小的离地事件}\rightarrow\text{稳定恢复}\rightarrow\text{较多奖励}
\]

对于尚未发现大跳跃的策略，后一条路线可能更容易获得收益。

**建议修改方式：主要恢复收益与合格跳跃关联，弱恢复引导仍然保留。**

例如：

\[
r_{\mathrm{recover}}
=
w_{\mathrm{task}}
\mathbf 1_{\mathrm{qualified\ landing}}
Q_{\mathrm{recover}}
+
w_{\mathrm{weak}}Q_{\mathrm{safe\ settling}},
\]

其中第二项应当较小、累计收益有界，不能代替主要任务。

不建议把未达标跳跃后的全部恢复奖励直接归零，否则又会失去有用的训练引导。**这是需要设计新奖励版本，而不是放松原验收标准。**

## 问题二：固定 COM 参考时序，与已经观察到的可行动作不一致

当前 v2c 使用了一个手写的定时 COM 参考：

\[
z_{\mathrm{ref}}(t)
=
z_{\mathrm{reset}}
-0.06e^{-((t-0.93)/0.12)^2}
+0.14e^{-((t-1.25)/0.19)^2}.
\]

也就是大约在 0.93 秒下蹲，在 **1.25 秒达到抬升峰值**。

但那条完整成功的工程轨迹：

- 约 **1.282 秒才离地**；
- 约 **1.536 秒落地**。

这意味着：

> **你们当前提供给 PPO 的参考，已经要求 COM 接近峰值时，一条已知可行轨迹才刚刚准备离地。**

这不能证明“1.25 秒到峰值一定不可能”，但足以说明：**这个参考并没有经过现有可行轨迹的验证，不能默认它就是正确引导。**

而且，当前参考使用相对 `reset_com_height` 的变化；正式验收衡量的则是**实际离地后**的 COM 上升。两者并不是同一个量。 

### 下一步怎么验证？

先不要立即再设计一条新曲线。让 Codex 对同一组诊断场景输出：

```text
实际 COM
参考 COM
COM 竖直速度
实际起跳/落地时刻
height_tracking 奖励
flight 奖励
recovery 奖励
各项惩罚
```

比较零动作、现有工程控制器、200 更新策略和最新策略。

需要回答的是：

**已有可行动作是否能得到合理的训练回报？不跳或小幅振荡的行为，会不会反而在某些主要奖励项上更有利？**

没有这个分项诊断，继续调整奖励权重很容易变成盲调。

## 问题三：高斯探索越来越大，但有效动作被截断了

当前策略先产生无界高斯动作，再由环境截断到 \([-1,1]\)，随后映射为关节目标。

在同一个状态下：

\[
a_{\mathrm{train}}
=
\operatorname{clip}(\mu+\sigma\epsilon),
\qquad
a_{\mathrm{eval}}
=
\operatorname{clip}(\mu).
\]

一般而言：

\[
\mathbb E[\operatorname{clip}(\mu+\sigma\epsilon)]
\neq
\operatorname{clip}(\mu).
\]

因此，**随机训练时表现尚可，并不保证确定性均值动作也表现相同**。

现有诊断已经观察到这个差异：

| 控制方式 | 非足端触地 | 跳跃表现 |
|---|---:|---|
| 零动作 | 0/32 | 没有跳跃 |
| 确定性策略 | 32/32 | 没有合格跳跃 |
| 随机策略 | 0/32 | 没有合格跳跃，最大 COM 上升约 4.38 mm |

该诊断记录的均值动作还出现了 `2.1549`、`-1.5777` 等明显超出执行边界的值；随机策略的平均最大关节速度约为 29.63 rad/s。

**这支持调查“噪声—截断—均值控制”之间的关系，但不能直接断言 PPO 实现错误。** 连续动作裁剪本身是已有研究明确讨论的问题，不能仅凭存在裁剪就判定策略梯度失效。[arXiv](https://arxiv.org/abs/1802.07564?utm_source=chatgpt.com)

### 为什么“std 改成 0.15”还不一定解决问题？

仓库中的额外方案已经计算过：对所选初始状态，将 std 降为 0.15 后，平均裁剪概率仍约为 **49.45%**。这提示不少均值已经在边界附近或边界之外。

因此存在两种不同问题：

**噪声太大：** 采样动作与确定性动作差异大，稳定恢复困难。  
**均值饱和：** 大量不同原始动作被映射为同一个极限目标，减小噪声后可能更难探索回来。

只降低 std，可能改善第一种，却未必解决第二种。

另外，我核对了训练入口：**`--init-checkpoint` 加载后确实显式重设了 `log_std/std`，这一处没有遗漏。** 应增加生效值断言，而不是重复修复一个不存在的问题。

# 三、额外低噪声方案：值得做，但只能当短对照

我的建议是：

**保留该方案，但不要把它当作下一轮唯一的主攻方向，更不要预设再跑 200 更新就会成功。**

从 `corrected_v2c_main01` 初始化、采用 `std=0.15` 和 `entropy=0`，是一个比较清楚的假设检验：检查缩小训练与确定性执行差异后，原 v2c 奖励是否能推动均值策略产生有效动作。仓库已经明确提出这个方案，且尚未执行。

建议调整为以下执行方式，**须在得到额外修订授权之后进行**：

| 项目 | 建议 |
|---|---|
| 初始化 | 使用 200 更新时相对稳定的权重，不用最新退化权重 |
| 第一检查点 | 先做 50 更新的小试，而不是无检查地跑完 200 更新 |
| 快照 | 每 25 更新保存检查点与动作分布遥测 |
| 重点指标 | 合格飞行、实际起跳速度、均值越界、动作裁剪、触地和恢复窗口 |
| 对照限制 | 保持 v2c 奖励不变，避免把噪声修改和奖励修改混在一起归因 |
| 停止依据 | 没有出现有效跳跃信号，且饱和/触地明显恶化，则停止并记录“该改动不足” |

还要注意：**`entropy=0` 不代表 std 被固定。** 当前 std 仍是可学习参数，应监测它是否再次增长，而不是只记录配置中的初始值。当前策略和配置确实使用可学习对数标准差。

这条对照有价值，但它回答的是“低噪声是否改善当前训练”，不是“一定能找到跳跃技能”。

# 四、我更推荐的主线：自动教师引导，而不是继续纯随机探索

结合当前结果，我会把下一条工程主线设为：

> **已有受限动作搜索 → 可行轨迹数据 → 行为克隆初始化 → 低噪声 PPO → 撤除辅助，完整地面起跳评测。**

这仍然以 RL 为最终优化方式，但不要求它从 18 维、100 Hz 的独立随机动作中凭空发现整个发力时序。

## 1. 利用已经存在的低维协调结构

你们的 `isaac_jump_capability.py` 已经不是完全随机挥动 18 个关节，而是搜索约 8 个参数，包括下蹲时间、蹬伸时间、腿部协调幅度、前后偏置和收腿时间。它使用的仍然是原环境中的受限动作，没有给机器人额外悬空力。

这正是有用的先验：

```text
不是搜索每个时刻每个关节怎么动，
而是先搜索一套有物理意义的协调发力方式。
```

下一步可以围绕现有较好参数做局部搜索，重点改善**落地后的恢复**。但要在独立的训练初态集合上验证，不要把两个固定验收面板用于反复筛选教师。

## 2. 不要只模仿唯一成功轨迹

建议采集一组具有不同小扰动的轨迹，并保存：

\[
(o_t,a_t,q_t,\dot q_t,c_t,\text{事件状态}).
\]

其中，\(o_t\) 必须是实际策略使用的完整历史观测，不能事后根据摘要补造。

对失败轨迹要按阶段处理：

**有效起跳但恢复失败：** 可以利用起跳阶段，不能把摔倒后的动作当作正确恢复示范。  
**完整成功：** 可以用于整段模仿，但仍需独立闭环测试。  
**单纯站立：** 可作为恢复和稳定性辅助数据，但不能占据训练主体。

行为克隆只是让策略进入有用的动作区域。**离线动作误差低，不等于闭环运行会成功。**

## 3. 优先解决“跳起来以后怎么恢复”

现有精选动作重放的主要差距是：

\[
30/32\text{ 合格跳跃落地}
\quad\longrightarrow\quad
1/32\text{ 完整恢复}.
\]

虽然这不是鲁棒性估计，但它很适合指导下一步的工程训练分解。

我建议采用：

```text
从地面开始，执行已验证的专家前缀
                    ↓
到腾空后段或落地前，交给学习策略
                    ↓
先学会恢复
                    ↓
逐步提前接管时刻
                    ↓
最终由策略从地面控制完整动作
```

**当前不建议直接把机器人恢复到任意接触状态。** 你们的检查点机制明确只承诺 PPO 更新边界的规范地面重启，不承诺任意接触中途的 PhysX 状态重放。先从地面真实执行前缀，能够避免把未验证的中间状态恢复问题引入训练。

最终验收仍必须完全撤掉专家前缀，由策略自主完成全部动作。

## 4. 这条路线必须明确改变基线名称

建议保留两个独立分支：

| 分支 | 身份 |
|---|---|
| `G04-pure-ppo-low-noise` | 原奖励下的低噪声纯 PPO 对照 |
| `G04-guided` | 自动教师数据、行为克隆初始化与 PPO 微调 |

不能把第二条分支的结果继续称为“无先验纯 PPO”。教师搜索、数据采集和模仿学习的计算成本也要单独记录。

这不会削弱你们的研究方向。相反，**“用可计算的物理结构减少人工示范和无效探索”本来就与你们的目标一致。** 但它属于新的训练方法，需要明确记录，而不是悄悄塞进原基线。

# 五、下一轮的顺序应该怎样排？

我建议按下面四步推进，而不是继续沿原 G04→G05 自动执行。

| 步骤 | 具体任务 | 要得到的答案 |
|---|---|---|

| **B：短仿真诊断，不更新权重** | 同初态比较零动作、两个旧 checkpoint、工程控制器及不同噪声水平 | 主要差异来自动作分布、时序，还是恢复控制？ |

步骤 B、C、D 都涉及新的 GPU 作业，应继续使用现有预算保护与授权流程。**账面上还有预算，不等于额外训练修订已经获准。** 仓库记录的当前累计用量约为 3.4324 GPU-hours、9,968.5 万次交互，而且其中含有历史保守预留，不能把它们全部当作有效 PPO 训练量。

### 下一轮必须增加的诊断指标

除了总成功率，建议重点看这一条链：

\[
P(\text{离地})
\rightarrow
P(\text{合格飞行})
\rightarrow
P(\text{合格落地})
\rightarrow
P(\text{连续恢复}\mid\text{合格落地}).
\]

恢复再分解为姿态、水平速度、角速度、关节速度和支撑条件各自能连续满足多久。

这样才能区分：

**根本没学会蹬地；跳起来但姿态不对；已经落地但关节持续振荡；还是某一个恢复条件在不断打断计时。**

仅看 `reward` 和最终 0/400，无法有效指导下一轮。

```text
交付报告、代码差异、测试日志和待授权命令后停止。
```

**总的来说，现在最需要的不是更大的网络、更多 GPU 或更长续训，而是让训练信号明确指向“合格起跳后稳定恢复”，并让策略真正接触到这种动作序列。**

你们已经有足够的工程基础和少量可行轨迹支撑这一步。接下来应把它们转化为可重复的学习信号，再讨论空中挥拍和扣杀。
