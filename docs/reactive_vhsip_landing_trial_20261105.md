# Reactive landing MPC/VHSIP 试验报告（2026-11-05）

## 结论

本轮把 [Reactive Landing Controller](https://github.com/iit-DLSLab/reactive_landing_controller) 的 VHSIP（Variable Height Springy Inverted Pendulum）水平捕获点思想接入 Go2+PiPER+球拍的现有 Isaac 控制接口，并在固定 128 个 TRAIN 条件上完成了一次原生仿真试跑。

**当前结果没有超过基线：**

| 指标 | 冻结基线 | VHSIP 试验（8 个指定案例启用） |
|---|---:|---:|
| complete5 | 27/128 | 27/128 |
| 合格空中拍线触球 | 74/128 | 74/128 |
| 条件恢复 | 34/128 | 34/128 |
| 实际球拍接触 | 110/128 | 110/128 |
| 越网 | 71/128 | 72/128 |
| 合法落区 | 64/128 | 63/128 |
| 数值故障 | 0 | 0 |

因此，本轮不能宣称 VHSIP 已经提高落地成功率；它证明了该批量计算和控制接口可以稳定运行，但当前接入层还没有把理论上的捕获点转化为可重复的着地收益。

## 使用的控制结构

论文原方法是面向 torque-controlled Go1 的 proprioceptive reactive landing controller，使用 VHSIP 计算竖直弹簧-阻尼轨迹，再用水平 ZMP/foot-placement 最优控制连续调整足端，落地后切换到阻尼参考轨迹。论文和代码：

- [论文：Reactive Landing Controller for Quadrupedal Robots](https://arxiv.org/abs/2305.07748)
- [官方实现](https://github.com/iit-DLSLab/reactive_landing_controller)

本项目当前采用的是**受限迁移版**：

1. 从公开状态估计根部姿态、质心速度、足端位置和足端接触；
2. 用实际加载的 Go2+PiPER+球拍模型做批量 FK/Jacobian；
3. 用 torch 在 GPU 上批量计算 VHSIP 的水平 capture/ZMP 偏移；
4. 将支撑中心沿捕获偏移移动，生成足端目标；
5. 用有限次数阻尼最小二乘 IK 求关节位置，再经过原有的 joint target rate limit、关节限位和位置 PD 下发；
6. 首次足端接触后，使用平滑的质心/姿态阻尼参考和已经存在的恢复辅助。

入口和实现：

- [`reactive_landing_v1.py`](../quadsmash/control/reactive_landing_v1.py)
- [`shared_target_assistance_v6.py`](../quadsmash/control/shared_target_assistance_v6.py)
- [`evaluate_shared_target_ground64_persistent_recovery_v1.py`](../scripts/evaluate_shared_target_ground64_persistent_recovery_v1.py)

本轮配置是 `prepare_and_buffer_vhsip`，VHSIP 内部使用 0.6 s 的短滚动窗口，IK 3 次，blend 0.08；只在 TRAIN 1、3、8、9、12、18、20、30 启用，目的是先观察明确失败案例，避免把 128 例全部变成控制器试验。

## 逐案例结果

与同 seed 的冻结基线比较：

- complete5、空中触球和条件恢复总数完全不变；
- 5 个案例的逐案例状态发生变化；
- TRAIN 22 的恢复状态由失败变为成功，但它本来不是完整成功，球侧条件仍未满足；
- TRAIN 72 的恢复状态由成功变为失败；
- TRAIN 12 的 `ball5_except_recovery` 由满足变为不满足；
- TRAIN 40 和 TRAIN 82 的 `ball5_except_recovery` 由不满足变为满足；
- 指定启用的 8 个案例中，完整成功数没有增加。

这表明控制器确实影响了落地轨迹，但当前修正方向和时序还不稳定，不能只看“有动作变化”就认定它在帮助恢复。

## 为什么当前不是“VHSIP 求解失败”

本轮 VHSIP 不是 OSQP/QP 形式的迭代求解，而是对论文中的水平单输入 OCP 做解析/批量矩阵传播。因此没有出现 `infeasible`、`maximum iterations` 等求解器错误；原生试跑数值故障为 0。

现有固定接触 support MPC 的审计也显示：真实 OSQP 失败只有 6 次（3 次达到最大迭代、3 次原始不可行），另有 44 次虽然 OSQP 返回 solved，但独立的物理残差检查未通过。大多数落地失败来自：

1. 选定的接触模式和实际首次触地不一致；
2. 支撑多边形/足端目标在剩余落地时间内不可达；
3. 位置 IK、关节速率限制和原有 PD 不能在接触前实现目标；
4. 接触冲击、身体非足部触地和持续稳定窗口没有进入 VHSIP 的预测模型；
5. 控制器输出的是关节位置参考，而论文输出最终由力矩级 WBC/执行器实现，二者之间缺少动力学闭环。

所以，“求解失败”需要分成三层：

```text
数学 OCP/QP 不可行
    → 目标在剩余时间内不可达
        → 目标可达但 IK/PD/速率限制没有执行出来
            → 执行出来但接触冲击或后续稳定窗口仍失败
```

当前 VHSIP 试验主要处在第三层和第四层，尚未证明第一层是主要瓶颈。

## 当前最可能的技术原因

### 1. 只调整水平支撑中心，没有真正改变落地冲量

VHSIP 给出了水平捕获偏移，但下游只将它转换为足端位置和关节目标。原有位置 PD 没有显式的质心动量、接触力、摩擦锥、碰撞冲量或触地顺序约束。因此，脚目标移动不一定能把机身角速度和落地冲击压下来。

### 2. 预测模型与实际落地状态不一致

当前使用固定质量、近似竖直高度和水平二阶传播，未把 PiPER/球拍摆动造成的构型惯量、全身角动量和关节限位纳入预测。对腾空挥拍后的 Go2，这个差异可能比 VHSIP 本身的水平捕获补偿更大。

### 3. 触地后的模式切换仍然由简单接触标志驱动

一旦观察到足接触，代码会切换到支撑/缓冲参考；但实际首次接触可能是单脚、边缘触地或身体先碰地。当前没有接触冲量估计、接触可信度和冲击后重新规划，所以“脚已接触”不等于“可用支撑已建立”。

### 4. 位置 IK 与速率限制消耗了有效落地时间

VHSIP 计算出的目标可能合理，但 3 次 IK、20 rad/s 速率限制、关节限位和下游 PD 共同造成跟踪滞后。离线比较表明，VHSIP 的初始足端目标误差只比旧模式略小；这不足以单独改变接触结果。

### 5. 当前实验只覆盖 8 个案例，且没有针对性地重算接触前的可行性

本轮是控制器接入试验，不是完整的落地 MPC 训练。它验证了接口和运行稳定性，不能据此判断所有失败案例都适合 VHSIP；也不能把 27/128 的不变解释为该方法在所有状态上无效。

## 能不能求解出来？

**有可能，但需要改变问题定义和执行接口。** 当前实现继续调 VHSIP 窗口、capture gain 或 IK 次数，最多改善参考轨迹，不能解决力矩/接触层的核心缺口。

建议下一阶段按以下顺序推进：

1. **先做接触前可行性筛选。** 在预计触地时间内同时检查足端位移、关节速率、支撑多边形和机身角速度是否可达；不可达时不要调用“成功落地”目标，而是选择最小风险的缓冲姿态。
2. **加入接触冲击后的短时重规划。** 首次足接触后使用实测接触足、根部速度和角速度重新计算支撑中心与足端目标，不继续追踪着地前旧计划。
3. **把控制变量从单纯关节位置扩展为关节速度/力矩或全身 QP。** 至少加入质心动量、角动量、接触力和摩擦约束；最终才接近论文中的力矩级闭环。
4. **先在固定失败案例上验证“落地状态改善”，再扩大到 128 例。** 评价应包括首次非足部接触时刻、触地足、根部角速度、最大身体接触力和稳定窗口，而不是只看 complete5。
5. **保持完整回合判定不变。** 球已经打好的回合，落地辅助不能通过牺牲出球、越网或落点换取“站住”。

## JAX/GPU 后续计划

当前 VHSIP 已经是 torch GPU 批量实现，但不是 JAX。只有在力矩/接触接口和目标定义稳定后，才值得做 JAX：

1. 把 `_vhsip_capture` 的固定步传播改写成纯函数 `jax.numpy`；
2. 用 `jax.vmap` 覆盖环境/案例，用 `jax.jit` 编译固定 horizon；
3. 用 torch 与 JAX 对同一批状态做数值 parity（capture offset、足端目标、边界情况）；
4. 先作为离线批量规划器和训练数据生成器，再考虑接入 Isaac 训练循环；
5. 在 parity 和原生落地收益都通过前，不替换当前控制器。

## 后续代码增量（尚未宣称原生收益）

在本报告之后加入了两个实验性组件：

- [`landing_support_mpc_v2.py`](../scripts/landing_support_mpc_v2.py)：在原固定接触 support QP 外增加质心投影/支撑裕度触发和终端可行性门。它仍然不能创建接触，也没有冲量模型；在 26 个失败案例的离线采样中，阶段 QP 仍可解，但终端支撑门仍经常不满足，因此暂时不把它接入正式策略。
- [`reactive_landing_vhsip_jax.py`](../quadsmash/control/reactive_landing_vhsip_jax.py)：可选的 JAX `jit/lax.scan` VHSIP 方程实现。当前环境没有安装 JAX，尚未做 Torch-JAX parity，也没有 GPU 加速结果；Torch 版本仍是运行基准。

这两项代码的目的分别是让“支撑域风险”可测量、让后续 GPU 批量规划有可复现的纯函数接口，而不是用未验证的离线结果替代原生落地评估。

## 支撑裕度 MPC v2 原生试跑

随后在同一冻结策略、同一 seed 和同一 128 个 TRAIN 条件上运行了 v2：

```text
landing_mpc_v2_supportmargin8_seed882072_01
```

配置启用了 TRAIN 1、3、8、9、12、18、20、30，5 步滚动 horizon、允许局部第一步纠正和 0.5 的软摆动足任务。控制器记录 731 次第一步应用、298 次完整 horizon 接受，数值故障为 0。

但是任务结果仍为：

| 指标 | 冻结基线 | 支撑裕度 v2 |
|---|---:|---:|
| complete5 | 27/128 | 27/128 |
| 合格空中拍线触球 | 74/128 | 74/128 |
| 条件恢复 | 34/128 | 34/128 |
| `ball5_except_recovery` | 53/128 | 53/128 |

逐案例结果没有变化。由此可以确认：**支撑裕度触发器能够提前并频繁地调用 MPC，但在当前固定接触 QP＋关节位置目标接口下，仍不足以改变延迟非足部触地或稳定窗口结果。** 这进一步支持“瓶颈在接触/动量闭环和执行接口，而不是触发器太晚或 OSQP 完全不可解”的判断。

本次试验输出位于：

`reports/G07_full_racket_v5/landing_mpc_v2_supportmargin8_seed882072_01/`

随后又运行了加入安全腿部姿态参考的 v2 试验：

```text
landing_mpc_v2_posture8_seed882072_01
```

该版本在首次足端接触后把腿部姿态参考向实际机器人默认腿姿态平滑混合，机械臂参考保持学生动作。它记录 337 次第一步应用、111 次完整 horizon 接受，但结果仍为 27/128、74 次合格空中触球、34 次条件恢复，逐案例的完整/恢复/球侧结果与基线完全一致。

这排除了“只缺一个默认腿姿态参考”这一简单解释：位置级 QP 确实在改变命令，但没有改变任务级落地事件。下一步若要继续追求收益，应把接触力/冲量和质心角动量纳入实际执行闭环，或直接采用可执行的力矩级 WBC；继续扫描 VHSIP 的 capture gain、窗口或姿态 blend 的边际价值已经很低。

另外对现有连续参考 QP 做了离线失败状态筛选：

- V3 使用硬 arm-command 保持，多个阶段在第 0–3 步因执行器/接触约束拒绝，不适合直接进入原生试验。
- V4 使用软 arm-command tracking，离线可行性接近 v2，但没有证据显示它会改变原生任务结果，暂不替换已测的 v2。

这两个版本作为可复现实验代码保留，后续只有在加入真实接触力/冲量或更准确执行器模型后才值得做原生试跑。

## 显式力矩 residual 试跑

为了验证“位置目标映射损失”是否是主要原因，评估入口又加入了 Isaac 隐式 PD 的 effort overlay：保持学生的位置目标不变，把 MPC 的总腿部力矩减去学生位置 PD 已产生的力矩，作为 `joint_effort_target` 叠加。

第一次试跑 `landing_mpc_v2_torque8_seed882072_02` 暴露了导出语义错误：虽然记录了 135 次 overlay，但 residual 约为零，因为代码先替换位置目标再计算 PD。该结果不作为力矩级证据。

修正后，`landing_mpc_v2_torque8_seed882072_03` 实际记录：

- 491 次非零腿部 torque overlay；
- residual 均值约 15.05 N·m，最大约 46.79 N·m；
- 数值故障为 0；
- complete5 仍为 27/128，合格空中拍线触球 74/128，条件恢复 34/128；
- 与基线逐案例的完整、恢复和球侧布尔结果没有变化。

部分案例在力矩 overlay 后更早结束，说明当前 Pinocchio 支撑模型给出的力矩方向/接触假设与真实 PhysX 响应仍有偏差。**这次试验排除了“完全没有把力矩送进执行器”这一解释，但没有证明当前力矩解可用于稳定落地。**

## 本轮证据

- 试验输出：`reports/G07_full_racket_v5/reactive_vhsip_actualfail8_seed882072_06/`
- 运行状态：GPU0，102400 env steps，约 0.322 GPU hours，正常结束
- 基线：`reports/G07_full_racket_v5/frozen_v2_smooth_approach16_frozen128_seed882072_01/`
- 当前实现提交：`4350c2e`

**结论：本轮没有找到“数学求不出来”的证据；更像是模型、接触模式和位置执行接口之间的能力不匹配。下一版应优先补上接触冲量/动量闭环和力矩级支撑，而不是继续盲目扫描单个 VHSIP 参数。**
