## 1. 当前结论

此前最高的落地 MPC 候选是：

`landing_mpc_v3_touchdown8_seed882072_04`

它在固定 128 例、5 m/s 完整任务标准下得到：

- `complete5=28/128`
- 合格空中拍线触球：`74/128`
- 条件恢复：`35/128`
- `landed_target=64/128`
- 数值故障：`0`
- 基线 27 个完整成功全部保留，新增 TRAIN 12
- MPC 检查 1786 次，应用第一步 1383 次
- 求解器失败 54 次，独立约束拒绝 49 次

该候选的 28/128 来自此前的固定参考试验；修正后的净空任务 `_05` 和连续参考 v3 对照均为 27/128，因此当前没有可复现的 MPC 提升。MPC 仍不能称为稳定落地控制器，主要问题仍是接触建模和执行接口误差。

## 2. 参考方法与当前系统的关系

上游 `reactive_landing_controller` 使用 VHSIP 模型，根据本体感觉估计的质心水平速度，在自由落体过程中连续重算足端位置；论文目标包括无反弹、躯干不触地、稳定站立和足端不滑移，实验对象是力矩控制 Go1。[上游代码](https://github.com/iit-DLSLab/reactive_landing_controller) [论文](https://arxiv.org/abs/2305.07748)

当前工程没有直接复制其 ROS/Gazebo 力矩控制器，而是保留 Isaac Lab 的原有位置目标/隐式 PD 接口，并增加：

1. Torch 版 VHSIP 捕获点计算；
2. Pinocchio 全身模型；
3. 固定观测接触模式的全身支撑 QP；
4. 短时域顺序滚动 MPC；
5. 支撑边界、终端可行性和触地阶段门控；
6. 可选的第一步应用、风险下降门槛和滞回保持；
7. 可选的腿部力矩残差叠加。

当前的 JAX 代码只覆盖 VHSIP 的解析水平子问题，已经完成 Torch/CPU JAX 数值一致性检查，但尚未替代全身 QP，也尚未有 CUDA JAX 训练结果。

## 3. 当前 MPC 的计算链

```text
公开观测
  -> Pinocchio 构造 q,v、接触集合和足端/质心几何
  -> 根据姿态、角速度、水平速度、支撑数、支撑边界计算风险
  -> 若需要干预，固定当前接触模式
  -> 求解短时域全身支撑 QP
  -> 顺序积分加速度得到下一预测状态
  -> 检查每个阶段和终端风险
  -> 取第一步关节目标或力矩残差
  -> 通过原有位置目标/隐式 PD接口发送
  -> 下一周期重新测量并重复
```

QP 中包含：

- 全身质量矩阵和非线性项；
- 质心、姿态和关节加速度软目标；
- 已观测接触足的接触加速度约束；
- 摩擦锥多边形；
- 关节力矩、位置和速度边界；
- 非接触足的可选摆动足落地目标；
- Pinocchio 动力学和独立残差复核。

V1 是固定接触顺序 QP；V2 增加支撑多边形/线段距离和终端支撑可行性；当前 touchdown 版本允许一足状态继续滚动、对未接触足施加软落脚目标，并用风险下降门槛和 40 tick 滞回避免每个 tick 反复接管。

## 4. 为什么会出现“求解失败”

### 4.1 固定接触模型不能表示真正的触地事件

QP 将当前 `state.contacts` 当成整个预测窗口的已知接触集合：

- 已接触足有反作用力变量；
- 未接触足的力被固定为零；
- 预测中不会创建新接触；
- 没有碰撞冲量、接触建立瞬间的速度跳变，也没有接触模式搜索。

但真实失败通常发生在“脚先接触、随后机身/机械臂等非足部触地”或“未接触脚突然撞地”的切换过程中。这个阶段正是固定接触模型最不准确的地方。

因此会出现两类结果：

- 真实世界即将触地，但模型只允许旧接触模式，无法找到满足全部约束的预测；
- 模型找到旧模式下的可行解，但真实 PhysX 发生新接触后速度和支撑力突变，下一 tick 的模型状态已经偏离。

这不是纯粹的数值问题，而是模型没有包含需要求解的事件。

### 4.2 规划变量和真实执行接口不一致

QP 直接优化理想的全身加速度、接触力和总关节力矩，随后通过：

[
q_{\rm target}
=
q+\frac{\tau+k_d\dot q}{k_p}
]

反解成关节位置目标，再交给原有隐式 PD、限速和饱和执行。

这一步不是无损的力矩控制。当前诊断已经观察到：

- 力矩残差叠加路径确实被执行；
- 但 QP 总力矩与实际 PD 产生的力矩存在明显差异；
- 既有一次力矩残差均值约 15.05 N·m、最大约 46.79 N·m，却没有带来任务提升。

所以，模型中“支撑住质心”的力矩不一定会在 PhysX 中以同样方向和幅值出现。位置目标限幅、速度限幅、关节阻尼、执行延迟和隐式 PD 还会进一步改变它。

### 4.3 Pinocchio 模型没有完整包含原生执行和碰撞动力学

当前模型使用保存的刚体质量和惯量，但明确没有隐式加入：

- 电机转子/臂ature；
- 关节摩擦和反向间隙；
- Isaac 隐式 PD 的离散实现；
- 关节命令延迟和限速；
- PhysX 接触刚度、阻尼和碰撞冲量；
- 球拍、机械臂和机身首次触地的接触几何响应。

因此，QP 的动力学可行只代表“作者模型中的瞬时可行”，不代表 Isaac 执行后仍然可行。

### 4.4 终端判定和真实稳定判定不在同一层

MPC 的终端检查主要是：

- 倾角；
- 角速度；
- 水平速度；
- 足端数量；
- 质心到支撑线/支撑多边形距离。

正式回合还要求持续稳定窗口、不能发生非足部触地、不能破坏球侧条件。一个预测终端可能通过姿态和速度门槛，但实际触地后的瞬时冲量仍会导致后续非足部接触。

### 4.5 当前求解器失败和约束拒绝含义不同

当前 trial 04 的 54 次求解器失败，与 49 次独立约束拒绝不是同一回事：

- 求解器失败：OSQP 没有返回可用的有限解，可能是当前接触模式下数值病态或约束难以满足；
- 约束拒绝：OSQP 返回解，但在原始物理单位重新检查时违反动力学、接触、力矩、位置/速度或其他约束。

因此，“MPC 求解失败”不能直接解释为“落地状态在物理上无解”。还要看失败阶段的 `contacts`、风险、残差和首次非足部接触前后的状态。

## 5. 结合当前落地失败审计的判断

已有审计显示：

- 26 个球侧已经合格但恢复失败的回合；
- 这 26 个都出现了合格足部着地；
- 其中 22 个在着地后又发生非足部接触；
- 非足部接触发生在首次着地后约 0.333–3.707 秒，中位数约 1.935 秒；
- 22 个中有 19 个在 recovery gate 开放时仍然处于可接管状态。

这说明失败不是“脚完全没落地”，而是：

```text
首次足部接触
  -> 质心/角速度没有被持续收住
  -> 支撑区域或躯干姿态继续恶化
  -> 数百毫秒到数秒后非足部触地
```

当前 MPC 的一足扩展和滞回确实有机会改善其中一部分，但尚未解决接触建立后的动量闭环。trial 04 只新增 1 个完整成功，说明“更长接管时间”本身不是主要缺口。

## 6. 有没有可能求解出来

有可能，但不是继续盲目增加 horizon 或调一个风险阈值就能解决。建议按三层推进：

### 第一层：先让控制器在现有接口上稳定

1. 保存首次足接触后的真实状态窗口；
2. 记录足端接触建立、非足部接触首次出现、机身角速度、质心速度、关节目标和实际关节响应；
3. 用这些数据拟合执行器/接触延迟和有效力矩响应；
4. 将 QP 的预测模型改成带一阶执行器响应和动作延迟的模型；
5. 用平滑的 touchdown 参考和风险触发，不直接把理想总力矩硬反解成位置目标；
6. 接触建立后继续运行到稳定窗口，而不是只检查短 horizon 终端。

### 第二层：加入显式接触模式/冲量近似

短期不需要完整混合整数 MPC，可以使用少量预定义模式：

- 一足接触 + 目标落脚足；
- 两足接触；
- 三/四足稳定；
- 发生非足部接触时立即进入保护模式。

对新接触增加一个离散/软切换时间，使用冲量或速度重置近似；只在有限候选模式中选择代价最低且满足残差的轨迹。这样可以覆盖当前固定接触 QP 无法表达的关键事件。

### 第三层：再做 GPU/JAX 版本

JAX 化应分两步：

1. 先将单步动力学、足端 Jacobian、支撑风险、候选接触模式和短滚动统一成 `jax.numpy` + `jax.lax.scan`，使用固定维度和 padding，不在 jit 内创建 Python/OSQP 对象；
2. 再将 QP 改成可批量、可微或至少可 JIT 的求解器，如固定迭代的 primal-dual/ADMM，或使用 GPU 友好的批量约束投影/顺序二次近似。

不要把 CPU OSQP 直接包在 JAX 外面期待 GPU 加速。当前 JAX 只覆盖 VHSIP 解析子问题；全身 QP 仍是 CPU Pinocchio + OSQP，不能宣称已经完成 GPU MPC。

## 7. 推荐的下一步实现顺序

```text
A. 先记录失败窗口和实际接触事件
B. 用实际关节响应标定 position-PD -> torque 的有效映射
C. 在现有 CPU MPC 中加入执行器延迟和 touchdown 事件近似
D. 只在一足/两足有限模式中选择可行方案
E. 在固定 128 例上验证“旧27保留、新成功增加、非足部接触下降”
F. 再将风险、动力学和有限模式滚动移植到 JAX
G. 最后用 GPU 批量训练/蒸馏恢复策略
```

验收不应只看 OSQP solved 比例，至少同时看：

- 非足部接触率；
- 首次足部接触后 2 秒内稳定窗口；
- 球侧条件是否保持；
- 原 27 个完整成功保留/丢失/新增；
- 求解器失败、约束拒绝和实际执行偏差分别统计；
- MPC 开启/关闭的同一冻结策略对照。

## 9. 修正后的非足部净空原生试验

为验证“落地后大腿/机身连杆再次碰地”这一失败模式，我在同一冻结策略、同一 128 例面板和同一 MPC 参数下启用了 `nonfoot_clearance_weight=20`。试验输出为：

```text
reports/G07_full_racket_v5/landing_mpc_v3_clearance20_seed882072_05
git: 21f65aa（净空 `_05` 运行时）
GPU0: 0.3556 GPU h，102400 env steps，SUCCEEDED
```

先前的 `_04` 不能作为控制结果：净空分支缺少标量目标的向量维度包装，1433 次尝试都在 Python `ValueError` 中退出，最终只是原策略 27/128 的回退结果。修复后 `_05` 的可比较结果是：

| 指标 | 固定接触 MPC `_04`（净空未执行） | 净空 QP `_05` | 旧基线/判断 |
|---|---:|---:|---|
| 完整成功 `complete5` | 27/128 | **27/128** | 没有提升 |
| 合格空中触球 | 74 | **74** | 未改变 |
| 条件恢复 | 34 | **34** | 未改变 |
| 实际球拍接触 | 110 | **110** | 未改变 |
| 越网 | 71 | **71** | 未改变 |
| 目标落点 | 64 | **63** | 略降 |
| 数值故障 | 0 | **0** | 数值稳定 |

`_05` 中 MPC 记录了 1954 次事件，1830 次首步尝试进入执行路径，270 次 QP 首步被接受；83 次属于 solver failure，101 次属于约束/终端拒绝，1433 次因为预测终端支撑裕度没有达到而拒绝，67 次没有触发风险门控。预测接触模式仍为 0 次，说明当前 8 步滚动仍没有在预测中可靠地产生新的足部接触。

因此，当前落地失败的结论更明确了：**MPC 不是完全求解不出来，而是只在一部分当前接触模式和局部风险状态上有可执行解；这些局部位置控制在真实 PhysX/隐式 PD 下没有把后续 1–3 秒的动量和非足部接触收住。** 净空任务的 QP 形式已经可以运行，但没有改善完整回合，反而在一个目标落点指标上少了 1 例。

这也暴露出当前实现的两个结构性限制：

1. 净空任务只是软加速度代价，不是对大腿、球拍或机身碰地的硬接触约束；它不能产生新的支撑力或碰撞冲量。
2. MPC 仍使用由公共观测反解出的 Pinocchio 状态、作者标注的刚体质量和即时位置 PD 映射，未包含 PhysX 的电机惯量、摩擦、隐式积分和碰撞冲量。因此 QP “solved”只代表模型内局部可行，不代表原生执行后的落地状态会按预测演化。

下一步不应继续单独扫描净空权重。优先记录首次足部着地到非足部接触之间的真实关节目标、实际关节状态、机身角速度和接触部件，随后把执行器延迟与有限接触模式加入预测。只有在 CPU 版本能稳定降低非足部接触后，才值得把固定维度动力学和有限模式滚动移植到 JAX/GPU；直接把 OSQP 包在 JAX 外不会得到 GPU 加速。

## 10. 连续参考 v3 原生对照

为排除“每个控制 tick 重置 COM/支撑参考、机械臂目标变化过快”这一因素，我将已有 `LandingSupportMPCV3` 接入评估入口，启用连续 COM 参考、支撑锚点和机械臂位置命令保持，其他条件与净空 `_05` 完全一致。试验输出为：

```text
reports/G07_full_racket_v5/landing_mpc_v3_continuous_clearance20_seed882072_01
git: 7f1c189
GPU0: 0.3556 GPU h，102400 env steps，SUCCEEDED
```

结果：`complete5=27/128`、合格空中触球 `74/128`、条件恢复 `34/128`、实际球拍接触 `110/128`、越网 `71/128`、目标落点 `64/128`、数值故障 `0`。MPC 记录 1334 次，只有 133 次首步被应用；1188 次为求解失败，63 次为约束拒绝，83 次未触发风险。主要失败状态是预测第 0–2 阶段的 `primal infeasible`，原因是连续参考和保留机械臂命令同时施加后，瞬时位置/速度/力矩边界没有可行交集。

因此，连续参考解决了参考重置问题，但没有解决真实落地的主瓶颈，且在当前位置 PD 接口下会明显压缩 QP 可行域。它应保留为可复现实验分支，不应作为下一轮默认控制器。

## 11. 结论

当前证据支持：

- MPC 有部分可行解，并已在固定面板增加 1 个完整成功；
- 失败主要来自接触模式、冲量、执行器接口和模型误差的组合；
- 不能将 OSQP 的失败等同于物理无解；
- 继续加长固定接触 horizon 的收益有限；
- 先做接触事件/执行器闭环，再做有限模式 MPC，最后做 JAX/GPU 批量化，成功概率最高。
