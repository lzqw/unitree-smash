# 多状态恢复搜索：轮流提交候选

2026-11-09。纯控制恢复；没有RL、BC或蒸馏。

## 修改原因

当前V7对每个初态连续提交一组候选，再提交下一个初态，所有工作共享固定截止时间。每个候选执行时间不同，较晚提交的初态可能得到更少搜索机会。这是代码结构存在的调度风险，**尚无逐状态CPU耗时证明它解释了当前多少失败**，不能据此把已有失败改判为成功。

新增 `scripts/search_dense_prefix_recovery_v8.py`，轮流为各初态提交一个候选，每轮覆盖全部初态后再进入下一轮。工作完成后立即收集，每八项更新一次逐状态进展。记录实际工作进程CPU时间、墙钟时间、排队等待、计算预算不足数量、完整路径及末段稳定通过数。

轮流提交不保证CPU时间完全相等；持续更久的物理轨迹本来就更昂贵。新增指标用于判断分配是否合理，不要求通过缩短物理轨迹来人为凑齐数量。

## 保持不变

原始实际初态与已检查的模型前缀、18维命令范围、160子步物理模型、碰撞检查、原8秒结束时间、稳定窗口、候选扰动分布、评分优先级及总计算上限均保持。候选分数相同则使用提交序号确定顺序，避免完成先后顺序影响同分候选选择。

模型中间状态仍明确标为模型预测，未在原生Isaac中传送。未通过完整原生执行的轨迹不作为正确专家标签。
